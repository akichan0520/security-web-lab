# 分析の確度：何が分かれば、何と言える？

| 等級 | 必要な証拠 | 言えること | 言えないこと |
|---|---|---|---|
| 0 設定 | Suricataルールの `msg`/`sid` の表示 | その検知条件が定義されている | 通信・攻撃があった |
| 1 ルール有効 | `suricata -T`成功、ロードされたルール数 | 構文上ロード可能 | そのPCAPにマッチした |
| 2 検出 | `eve.json` の実際の `alert` + SID/rev | 当該設定の検出条件に一致した | 侵害に成功した |
| 3 パケット根拠 | PCAP、frame、再構成バッファ、`content` 条件照合 | 何に反応したか説明できる | 特定のマルウェアであることの十分条件とは限らない |
| 4 事象の裏付け | HTTP応答、後続通信、関連ログ | 攻撃試行や感染の可能性を詳細評価 | 感染成功の確証とは限らない |
| 5 ホスト証拠 | EDR、イベント、ファイル変化、メモリ証拠 | 観測範囲で侵害・活動の裏付け | 完全な侵害範囲の証明とは限らない |

### `suricata.log` にCVEがあるのに `eve.json` が空のとき

`error parsing signature` は、**そのシグネチャの読込失敗**です。そこから攻撃先IPは分かりません。「パターン名がある＝攻撃を検出」と誤読しないこと。PCAP演習なら実際にEVEアラートがあるか確認します。

### `pcap_cnt` とフレームの対応

[Suricata 8.0.7 EVE仕様](https://docs.suricata.io/en/suricata-8.0.7/output/eve/eve-json-format.html)ではPCAPモードの実パケットに `pcap_cnt` が付くと説明されています。内部擬似パケットには付かない場合があり、**検査は再構成されたストリームを対象にすることもあります**。該当番号は調査の起点であり、全ての一致バイトがそこにある保証ではありません。
